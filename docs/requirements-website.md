## 1. 目的と背景（業務要件）

### 1.1 背景
- 中小企業の情報システム部門・情報セキュリティ担当は、ISMS（ISO/IEC 27001）やIPAガイドラインの求める従業員教育を実施する必要がある一方、教材の作成やメンテナンスに時間を割けない。
- 本事業は、一定のクオリティを保ったセキュリティ教材をウェブサイトと学習アプリで提供し、企業の教育実施を支援することで、セキュリティ分野に貢献する。

### 1.2 サイトの目的
1. 教材（動画・解説記事・確認問題・チェックリスト）を公開し、誰でも学べる状態にする（周知・啓発）。
2. 教育サービスの内容と価値を伝え、学習アプリの利用登録・支援サービスへの問い合わせにつなげる（集客・導線）。
3. 教材のテーマとISMS管理策・IPAガイドライン項目との対応を示し、企業の教育計画に組み込みやすくする（信頼性）。

## 2. 対象ユーザー
- 中小企業の情報システム担当者・情報セキュリティ担当者（教材を探している人）
- 経営者・教育責任者（教育サービスの導入を検討する人）
- 一般の従業員（公開教材で学ぶ人）

## 3. 公式要件・ガイドからの根拠（サイトに関わるもの）

| 根拠 | 要点 | サイトへの要求 |

| JIS Q 27002 6.3 手引⑤ | 伝達チャネルはウェブサイト、ニュースレター、eラーニング等の複数形式を用いる | 動画・記事・問題集など複数形式で同一テーマを提供 |

## 4. 機能要件

### 4.1 ページ構成（現行サイトを基礎とする）
- トップ：サイトの目的、特集テーマ、教材への入口、アプリ・有料記事・支援サービスへの導線
- 動画一覧：YouTube Shorts教材へのリンクとテーマ別整理
- 教材・記事一覧：note基礎シリーズ等の解説記事へのリンク
- 素材集：テーマ別の確認問題・チェックリスト（印刷対応）
- 有料記事：note有料記事の紹介と購入導線
- セキュリティニュース：公的機関等の最新情報を集約した一覧（4.5。検索流入の入口）
- 支援・問い合わせ：サービス紹介と問い合わせ導線

### 4.2 教材の分類・表示
- テーマ分類は複合軸とする：「基本対策（IPA 6か条対応）」「脅威・場面別（メール、テレワーク、内部不正等）」「対象者別（経営者／全従業員／新入社員／管理者・情シス）」。
- 対象者別の見せ方：経営者向けはリスクとコストの軸（事故時の損失額と対策コストの比較）で示し、従業員向けは日常の行動に直結する内容とする（アプリ要件定義書2節の「立場ごとの関心と見せ方」と共通）。
- 各テーマに、対応するISMS管理策（附属書A）とIPAガイドライン項目を明示する。
- 大きく表示する画像は、そのページ・記事の内容が一目で分かるアイキャッチとする（現行運用を要件化）。

### 4.3 更新管理
- 教材・記事の追加、差し替え、公開日・更新日の管理ができること。
- 教材には版（バージョン）の考え方を持たせ、改訂履歴を追えること（アプリ側の教材版管理と整合させる）。

### 4.4 計測
- アクセス解析により、テーマ別の閲覧状況を把握し、教材の改善・追加の判断に使うこと。

### 4.5 情報アグリゲーションと検索流入（2026-11-21 追加）
- サイトに「セキュリティニュース」セクションを設け、公的機関等の最新情報（注意喚起・脆弱性情報等）を集約して公開する。情報をまとめて見られる入口とすることが目的で、検索エンジン経由の流入（Google検索の上位表示）も狙う。
- 情報源と収集方法は、アプリ要件定義書4.9の収集設計（公式フィードの定期取得）と共通とする。表示は「見出し＋発表日時＋自前の3行程度の要約＋出典リンク」とし、本文の転載はしない。要約は出典本文のコピーではなく自前で作成する（著作権への配慮と、検索評価上の独自性の確保を兼ねる）。
- 分類はアプリ側と共通の3軸（情報の種別／脅威・手口／対象製品・機器）とし、カテゴリ別の一覧ページを用意する。脆弱性情報は製品名・CVE番号など具体的な検索語に対応しやすい。
- 表示範囲：サイトの一覧は最新100件（公式セキュリティ情報60件＋言語・ランタイム公式情報40件の2ブロック構成）とし、個別ページは全件を蓄積として残す（2026-11-28 実装値として確定）。過去分を含む全件の検索・自社向けの抽出はアプリ側の役割とする。
- 収集の運用：公式フィードの自動収集は1日2回（05:30／18:00）。収集スクリプト（scripts/collect_news.py）が個別ページと発見用ファイルを再生成する。
- 言語・ランタイム系の収集ソース（2026-11-28 拡張）：Python、Node.js、PHP、Go（公式ブログ＋Go脆弱性DB）、Rust、.NET、Ruby、C++（Microsoft C++ 公式ブログ）に加え、脆弱性データベース系として Java（GitHub Advisory Database の Maven）と C#（同 NuGet）を収集する。C／C++は言語公式の脆弱性データベースが無いため、公式ブログと JVN・IPA 側での検出でカバーする。GitHub Advisory Database の取得は、GitHub Actions 上では GITHUB_TOKEN を使う（無認証はIP単位の回数制限があるため）。
- 各情報から関連する教材・記事・動画へ内部リンクを張り、流入を教材とアプリの案内へつなげる。
- SEOの基本方針：速報性（収集から公開までの速さ）、自前要約による独自性、カテゴリの網羅、内部リンクの整備を基本とし、転載中心の構成にはしない。
- 有料側の付帯機能（自動収集、カテゴリ分け、保存、URLの最新化）はアプリ側の役割とし、サイト側は掲載と出典への遷移に徹する（アプリ要件定義書4.9）。

### 4.6 広告枠（上位表示の掲載依頼への対応）
- セキュリティ関連サイト・ニュースサイト等から上位表示の掲載依頼があった場合に対応できるよう、広告枠の仕様を用意する。
- 掲載枠は通常の並び順（編集上の並び）と分けて管理する（位置、期間、表示ラベルを設定可能にする）。
- 広告である旨の表示（「PR」「広告」等）を必須とする（景品表示法のステルスマーケティング規制への対応）。
- 有料掲載のリンクには rel="sponsored" を付ける（検索エンジンの有料リンクポリシーへの対応）。
- 料金体系と掲載条件は未決事項（9節）とし、依頼が発生した段階で確定する。

### 4.7 URL設計（2026-11-28 追加）
- 各画面にパス型の固有URLを持たせる：トップ（/）、セキュリティニュース（/news）、記事一覧（/articles）、動画一覧（/videos）、素材集（/materials）、有料記事（/paid）、支援サービス（/support）。ニュース個別ページは /news/<ID>、note記事のティザーページは /articles/<記事ID>。
- 実装方式：画面は1つのHTML内のJavaScriptで切り替える構成のため、Cloudflare Pages の _redirects（200リライト）で各パスへ本体を割り当て、開いたパスに応じて初期表示する画面を切り替える。画面ごとにタイトルと説明文（meta description／OGP）も出し分ける。ハッシュ形式（#news 等）も併用可能とする。
- 正規URLは拡張子なし・ドメインは apex（https://job-and-it-lab.com）に統一し、サイトマップと canonical はこの形式で記載する。
- 狙い：検索エンジンが画面・記事ごとに別のページとして認識できること。ハッシュだけでは別ページとして扱われないため、パス型を正とする。

### 4.8 note記事のサイト掲載ページ（2026-11-28 追加、v0.3で掲載量を改訂）
- note記事ごとに、サイト内に静的な個別ページ（/articles/<記事ID>）を用意する。検索エンジンとAIが本文テキストを読める形で掲載する。
- 掲載量は記事の種類で分ける（2026-11-28から2週間の試行。サイトの滞留時間を確保する狙い。効果はGA4の滞在指標とnote閲覧数の推移で測り、継続・拡大・中止を判断する）：
  - 基礎シリーズ：全文を掲載する。
  - 有料記事：note の無料公開部分の全文を掲載する。有料部分は公開APIが返さないため載せない（公開APIが返す範囲を超えて載せない）。
  - ニュース解説・AI・業務改善・特集：冒頭のみ（本文の約35％を目安に、見出しの途中では切らない）を掲載し、続きは note へ誘導する。
- ページ末尾に note への案内とリンクを置く（全文掲載の記事は「noteでも公開しています」、冒頭のみの記事は「続きは note で読めます」）。リンクには計測用のパラメータ（UTM）を付け、サイトから note への流入を測れるようにする。
- 生成は自動化する：note 同期（scripts/sync_note.py）の後に掲載ページ生成（scripts/build_teasers.py）が走り、新規・更新記事のページを作る。記事一覧の画面内のカードとトップページの新着記事は、サイト内の記事ページ（/articles/<記事ID>）へリンクする（v0.4で note への直接リンクから変更）。
- 表示仕様（v0.5で追記）：記事ページはブラウザ・OSのダークモード設定に追随し、配色は本体サイトのダークテーマ（背景 #141414、文字 #EDEDED）に合わせる。モバイル表示では、長い文字列（URL等）を折り返し、表・埋め込み要素のはみ出しを防ぎ、小画面向けに余白を調整する。

### 4.9 AI向け情報提供（2026-11-28 追加）
- 目的：AI検索（ChatGPT検索、Perplexity、GoogleのAI Overviews等）がサイトの内容を読み取り、回答の中で引用・リンクしやすくする。サイト流入目標（1万セッション）のうちAI経由の増加を重視する方針に沿う。
- 仕組み：
  - llms.txt：サイトの構成と全ページの一覧をAI向けに記載したファイル。発見用ファイルの生成時に自動更新する。
  - 構造化データ（JSON-LD）：トップページに WebSite、各ティザーページに Article を埋め込み、タイトル・著者・公開日・要約を機械可読にする。
  - RSSフィード（rss.xml）：セキュリティニュースと記事の新着を配信する。
  - robots.txt：AIクローラーを含め全許可とし、サイトマップの場所を示す。
  - サイトマップ（sitemap.xml）：全ページ（画面・ニュース個別ページ・ティザーページ）を載せる。
  - 前提として、AIクローラーはJavaScriptをほぼ実行しないため、本文は静的HTMLに書かれていること（ニュース個別ページとティザーページが該当）。

### 4.10 週次UI/UX改善サイクル（2026-11-28 追加）
- 毎週土曜21:00に、サイトのUI/UX分析（実ページの確認とアクセス数値）と修正案を提示し、事業者とチャットで議論する。
- 修正の実施とデプロイは、議論で合意してから行う。分析だけでサイトを変更しない。
- 指摘と決定は状態メモに残し、同じ指摘の繰り返しと、決定した修正の未実施を防ぐ。

### 4.11 動画一覧ページ（2026-11-28 追加）
- YouTube Shorts 動画シリーズの一覧画面（/videos）を設ける。公開済みの動画を新しい順に、縦型のサムネイルとタイトルで並べる。
- サムネイルとタイトルは YouTube の動画へリンクし、カードには同じテーマの解説記事（サイト内の記事ページ /articles/<記事ID>）へのリンクも併記して、サイト内での回遊につなげる。
- 紹介文やカードに「第○回」等の回数表示は入れない（動画シリーズの表記ルールに合わせる）。トップページの動画紹介も同じ扱いとし、動画一覧への導線を置く。
- 案内文では、社内のセキュリティ教育・研修に教材としてそのまま使えることを伝える（教材として社内で活用してもらう位置づけ。v0.8で明記）。
- 動画が増えたら一覧へ追加する（現行はサイト側のデータ配列で管理）。

## 5. コンテンツ要件（品質基準）
- 用語は公式ドキュメント・規格（JIS Q 27000／27001、IPAガイドライン等）の体系的な用語を使う。独自の造語は使わない。
- 教材は「1テーマ短時間で完結＋末尾に確認問題」の単位を基本とする。
- 素材（音楽・画像・フォント）は採用前に利用条件を確認する。参考画像は参考のみとし、そのまま使わない。
- フォントはGoogle Fonts「Noto Sans JP」（読みやすさのためゴシック統一）。デザイン規則は現行の確定事項（白基調、ネイビー#14213Dはボタン専用、ゴールド#FCA311は小アクセント専用、罫線1px統一、余白スケール8の倍数、3幅レスポンシブ）を維持する。
- スマートフォン幅（640px以下）では、素材集のテーマカードの大きな画像（テーマ画像）は表示しない。タイトルと説明文のみで内容を伝える（v0.6で追加）。

## 6. 非機能要件
- 対応端末：スマートフォン、タブレット、PCの3幅で読みやすく表示されること。
- 表示性能：画像は内容が伝わる範囲で軽量化し、モバイル回線でも実用的な速さで表示されること。
- 検索・共有：検索エンジンに正しく拾われる基本構造（タイトル、説明文、OGP）を備えること。
- セキュリティ：問い合わせ等で個人情報を扱う場合は、収集項目を最小限にし、取扱いを明示すること。
- 可用性：無料ホスティングの範囲で安定公開し、障害時は代替公開手段を検討できること。

## 7. 開発から運用保守・改善までの流れ

### 7.1 開発フェーズ
1. 要件定義（本書）→ 2. ワイヤーフレームでラフ確認 → 3. デザイン確定 → 4. 本編構築 → 5. 内容・リンク・表示の検証 → 6. 公開
（現行サイトはこの流れで構築・改修済み。今後の改修も同じ手順を踏む。）

### 7.2 運用保守（定常）
- 教材の追加・差し替え：動画・記事の公開に合わせて随時。
- 内容の定期見直し：IPA「情報セキュリティ10大脅威」の年次更新、および規格・ガイドラインの改定に合わせてテーマと教材を見直す。
- リンク切れ・表示崩れの点検：月1回を目安。
- アクセス解析の確認：月1回、テーマ別の閲覧傾向を記録する。
- 自動収集・同期：ニュース収集は1日2回（05:30／18:00）、note記事の同期は毎日22:30。GitHub Actions のワークフローが本線で、移行の検証が済むまで Muse 側の代替ジョブを併行稼働させる。
- デプロイ方針：Cloudflare Pages のデプロイ回数には上限があるため、変更はまとめて1回のデプロイで反映する。検証のための小刻みなデプロイはしない。
- サイトの脆弱性診断：週1回、公開サイトの応答ヘッダーや公開ファイルの露出を確認し、前週比で報告する。
- UI/UXの見直し：4.10 の週次サイクルで行う。

### 7.3 改善
