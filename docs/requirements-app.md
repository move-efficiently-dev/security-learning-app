# 学習アプリ要件定義書（ドラフト v0.1）

- 仮称：仕事とITの研究所 学習アプリ（セキュリティ教育サービス）
- 作成日：2026年11月21日
- 形態：ブラウザで動くウェブアプリ（スマートフォン・PC両対応）。ネイティブアプリは将来検討。
- 本書はドラフトであり、未決事項は第10章に集約する。
- 承認記録：2026年11月21日、事業者が「いったんOK」として本ドラフトを承認。未決事項（第10章）は残したまま、試作版の開発へ進む。

## 1. 目的と背景（業務要件）

### 1.1 背景
- 中小企業の情報システム部門・情報セキュリティ担当は、ISMS（ISO/IEC 27001）やIPA「中小企業の情報セキュリティ対策ガイドライン」の求める従業員教育（実施・記録・評価・改善）を回す必要があるが、教材の作成やメンテナンスに時間を割けない。
- 本アプリは、一定のクオリティの教材を配信し、受講・理解度確認・集計・催促までを自動化することで、担当者の負荷なく教育のサイクルを回せるようにする。

### 1.2 アプリの目的
1. 教材の配信：動画・解説・確認問題をコースとして配信する。
2. 理解度の確認：問題バンクからランダムに出題し、答えの丸暗記を防ぐ。
3. 記録と証跡：誰が・いつ・何を・どの結果で修了したかを保持し、審査・点検で提示できる形で出力する。
4. 集計と改善：組織・部署ごとの達成度を可視化し、弱点テーマを次の教育に活かせるようにする。
5. 継続の仕組み：リマインドにより未受講を減らし、定期的な再教育を回す。

## 2. 対象ユーザーと権限

| 役割 | 主な利用 | 主な権限 |
|---|---|---|
| 経営者 | 実施状況の把握 | サマリーレポートの閲覧 |
| 教育責任者（管理者） | 教育の運営 | 従業員の登録・部署管理、受講の割り当て、進捗・集計の閲覧、リマインド設定、記録の出力 |
| 部門責任者 | 部門の進捗確認 | 自部門の進捗閲覧、未受講者への催促 |
| 従業員（受講者） | 学習 | コース受講、確認テスト受験、自分の履歴・修了証の閲覧 |
| 提供者（運営） | サービス運営 | 教材・問題バンクの登録・改訂・版管理、配信管理、利用状況の確認 |

- 権限設計はIPAガイドラインの体制図（情報セキュリティ責任者、教育責任者、部門責任者）の役割分担に合わせる。

| JIS Q 27001 箇条7.3 認識 | 方針、自らの貢献、違反時の影響の認識 | 教材内容に方針・役割・違反時の影響を含める。顧客の方針を差し込めること |
| JIS Q 27001 附属書A 6.3 | 職務に関連する教育・訓練と、方針・手順の定期的な更新情報 | 定期配信・再受講、役割別カリキュラム、教材改訂と配信履歴 |
| JIS Q 27002 6.3 手引② | 初回教育は新規採用者と異動者が対象 | 入社・異動時の自動割り当て |
| JIS Q 27002 6.3 手引③ | 教育終了時に理解度を評価し、プログラムの有効性を確認 | 確認テスト、合否、達成度の集計 |
| JIS Q 27002 6.3 手引④ | 内容の5領域（経営層のコミットメント、ルールと義務、個人の責任、基本手順、連絡先とリソース） | テーマ分類は5領域をカバー。報告先・相談先は顧客固有情報を差し込み可能に |
| IPAガイドライン 1-7 | 教育は定期的実施、実施記録の保管、理解度と受講状況の評価結果を踏まえて改善 | 実施→記録→評価→改善のサイクル全体を機能として持つ |

| IPAガイドライン 1-9 | 点検では「対策を実行した証拠」となる記録を確認 | 記録は改ざんされにくい保管と、期間指定での出力・印刷に対応 |
| IPA ポイント学習 | 1テーマ5分完結＋確認テスト、対象者別コース | コース単位と対象者別コースの設計 |
| IPA 10大脅威 | 脅威テーマは年次で入れ替わる | 教材の年次見直しと追加を運用要件とする |

## 4. 機能要件

### 4.1 アカウント・組織管理
- 企業の登録（会社情報、管理者アカウント）。
- 従業員の登録・招待、部署の作成と所属管理。
- 入社・異動・退職に応じた受講者の追加・変更・無効化（ライフサイクル管理）。
- パスワード等の認証情報は安全に管理し、多要素認証の導入を検討する。

### 4.2 教材配信（コース）
- コース単位は「動画（約1分）＋解説＋確認問題＋チェックリスト」を基本とする。
- テーマ分類は複合軸：「基本対策（IPA 6か条・自社診断項目対応）」「脅威・場面別」「対象者別（全従業員／新入社員／管理者・情シス向け上級）」。
- コースには対応するISMS管理策とIPA項目を表示する。
- 管理者はコースを従業員・部署に割り当て、期限を設定できる。

### 4.3 問題バンクとランダム出題
- 問題はテーマ別のバンクとして保持し、確認テストではバンクからランダムに出題する。
- 同一受講者への連続出題で問題が重複しにくい制御（出題済みの管理）を行う。
- 合格基準（例：80%）と再受験を備え、不合格時は再受講・再受験へ誘導する。
- 間違えた問題の復習モードを用意する。
- 問題数の段階目標：開始時は4テーマで100〜200問、運用しながら1,000問規模へ拡大する（第10章の未決事項）。
- 問題の品質管理：出典（公式ドキュメント・規格）に基づく作成、答えと解説の照合を経たものだけを公開する。

### 4.4 受講・進捗管理
- 受講者：自分の受講状況、履歴、修了証（PDF）の閲覧・取得。
- 管理者：組織・部署ごとの受講率・達成度（平均点、合否、再教育状況）のダッシュボード、未受講者一覧。
- 記録の出力：受講記録一覧のCSV出力、期間指定出力、印刷対応（審査・点検の証跡用）。
- 弱点テーマの把握：テーマ別正答率を表示し、次の教育計画に活かせること。

### 4.5 リマインド
- 未受講者への自動催促（頻度は管理者が設定可能、初期値は週1回）。
- 管理者への定期レポート（月1回の進捗サマリー）。
- 入社時の自動割り当てと初回案内。
- 配信チャネルはアプリ内通知とメールを基本とする（詳細は未決事項）。

### 4.6 顧客固有情報の差し込み
- 顧客の情報セキュリティ方針、社内ルール、事象の報告先、相談先を教材内に表示できる設定枠を用意する。
- 入社時教育では「ルール説明＋理解確認＋誓約確認」の一連の流れを扱えるようにする（誓約の確認記録を保持）。

### 4.7 料金プラン（想定）
- 無料プラン：体験利用。確認問題は6問まで（教材の一部を体験可能）。
- 有料プラン：問題バンク全開放、受講記録・集計・リマインド・証跡出力を含む企業向け機能。
- 課金単位・価格・決済手段は未決事項（第10章）。

### 4.8 提供者側の管理機能
- 教材・問題の登録、改訂、公開・非公開の切り替え、版管理（いつ・何を変えたか）。
- 配信履歴の管理（どの版をいつ配信したか）。
- 利用状況の確認（登録企業数、受講総数等）。

### 4.9 情報アグリゲーション（セキュリティ情報の集約）
- サイトとの役割分担（2026-11-21決定）：アグリゲーションはウェブサイト側にも公開版（無料）を置き、情報をまとめて見られる入口＋検索流入の受け皿とする（サイト要件定義書4.5・4.6）。アプリ版は、自社環境プロファイルによる絞り込み、重要情報の通知、教材・学習記録との連携を有料の付加価値として差別化する。情報源とカテゴリ体系は両者で共通とする。
- 有料版の付帯機能（2026-11-21 ユーザー整理）：有料側の価値は情報そのものではなく、次の機能に置く。①収集機能（公式フィード等の自動収集）②カテゴリ分け機能（3軸分類の付与と、自社環境プロファイルによる抽出）③保存機能（全件の保持、検索、自社向けの保存）④URLの最新化（出典リンクのリンク切れ検知と、最新URLへの更新）。サイト側（無料）は著作権への配慮から「見出し＋自前の要約（一部のみ）＋出典リンクで出典へ遷移させる」構成に留める。
- 公式情報源（IPAの重要なセキュリティ情報・10大脅威、JPCERT/CCの注意喚起など）から、最新の脅威・脆弱性・注意喚起を集約してアプリ内に表示する。
- 表示形式は「見出し＋要約＋出典へのリンク」とし、本文の転載はしない（著作権への配慮）。出典と発表日時を必ず明示する。
- 情報はテーマ別（ランサムウェア、フィッシング、脆弱性、テレワーク等）に分類し、重要度の高いものが目立つ表示にする。
- 各情報に関連する教材（コース・確認問題）へのリンクを付け、「知る → 学ぶ」の動線を作る。これが他の集約サイトとの差別化点になる。
- 重要度の高い情報は、リマインドの仕組みと連携して管理者・受講者へ通知できるようにする。企業ごとに、通知するテーマの絞り込みを設定可能にする。
- 根拠：IPAガイドラインの経営者「重要7項目」取組7（最新動向を収集し関係者と共有する）、第2部の情報収集と共有の考え方。担当者が自力で情報収集する負荷を肩代わりする機能として位置づける。
- 収集設計（2026-11-21に公式情報で確認）：一次収集は公式フィードを正とする。IPA「重要なセキュリティ情報」RSS、JPCERT/CC RSS（統合版はJVN新着も含む）、JVN RSSの定期取得を主経路とする。フィードが確認できない情報源（国家サイバー統括室 cyber.go.jp 等）はWeb巡回・公式SNSによる補助確認に位置づける。
- 表示の上限：見出し＋発表日時＋自前要約（短文）＋出典リンクまでとし、全文転載は行わない。IPAは公式埋め込みサービス「icat for JSON」（会員向けサイトへの設置が公式に想定）の併用を検討する。
- 前提条件：JPCERT/CCは資料により商用転載の禁止や事前連絡の要求があるため、公開前に広報窓口へ商用利用の可否を確認する。確認が取れるまではJPCERT/CC由来の表示も最小構成（見出し＋日時＋リンク）に留める。政府機関サイトは利用条件を確認できたものから順次追加する。
- カテゴリ体系：集約する情報は次の3軸で分類し、組み合わせて絞り込めるようにする。
  - 情報の種別：注意喚起／脆弱性情報／インシデント・事例／対策ガイド・資料
  - 脅威・手口：ランサムウェア、フィッシング・不審なメール、ビジネスメール詐欺（BEC）、内部不正、標的型攻撃、AIをめぐるリスク 等
  - 対象製品・機器（脆弱性情報の主分類）：OS・PC（Windows、macOS）、スマートフォン（iOS、Android）、サーバー（Windows Server、Linux系）、ブラウザ（Chrome、Edge、Firefox等）、ネットワーク機器（ルーター、VPN装置、ファイアウォール）、言語・ランタイム・開発基盤（Java、Python、PHP、Node.js等）、クラウド・業務アプリ（Microsoft 365、Google Workspace等）、IoT機器・その他
- 脆弱性情報の集約：対象製品カテゴリごとに脆弱性情報を集約する。主な情報源はJVN／JVN iPedia（確認済み）、CISA KEV（悪用が確認された脆弱性の一覧）、主要ベンダーの公式アドバイザリ（Microsoft、Apple、Google等）を候補とし、フィードの有無と利用条件は情報源ごとに確認してから追加する。深刻度（CVSS等）と悪用状況（KEV掲載の有無）を併記し、優先対応すべきものが分かる表示にする。
- 自社環境との連動：企業は自社の環境（使用OS、スマートフォン、サーバー、主要アプリ等）をプロファイル登録でき、自社に関係するカテゴリの脆弱性情報だけを抽出表示・通知できるようにする。これにより「大量の情報から自社分だけを見る」負担軽減を実現する。

## 5. データ要件（受講記録）
- 記録項目：受講者（氏名・所属部署）、教材・コース（版を含む）、実施日時、確認テストの結果（得点・合否・出題された問題）、修了状態、誓約確認の有無。
- 保持期間：顧客のISMS運用・点検に耐える期間を保持する（具体的な年数は未決事項。退職者の記録の扱いを含む）。
- 記録の完全性：後から書き換えられない運用・仕組みとし、出力した記録は証跡として使える体裁にする。

## 6. 非機能要件
- セキュリティ：通信の暗号化、認証情報の保護、役割に応じたアクセス制御（最小権限）、操作ログの保持。
- 個人情報保護：受講者データは個人情報として扱い、収集目的・取扱いを明示する。提供者側の守秘体制も含めて運用ルールを定める（JIS Q 27001 附属書A 6.6の観点）。
- 対応端末：スマートフォンとPCのブラウザで利用できること。勤務場所を問わず受講できること（テレワーク対応）。
- 性能・可用性：中小企業の利用規模で実用的な応答と稼働を確保し、データのバックアップを定期的に行う。
- 使いやすさ：利用企業の教育担当者は専門家でない前提で、割り当て・集計・出力が迷わず操作できること。

## 7. 開発から運用保守・改善までの流れ

### 7.1 開発フェーズ（段階リリース）
1. 要件定義（本書）→ 2. 試作版（登録・受講・ランダム出題・集計・リマインドの最小構成）→ 3. 動作確認と内容の検証 → 4. 無料トライアル（知り合いの企業等で試用、フィードバック収集）→ 5. 課金機能の追加 → 6. 有料提供の開始。

### 7.1.1 開発環境・コード管理
- ソースコードとドキュメントは GitHub リポジトリで一元管理する（リポジトリ：security-learning-app、要件定義書・調査資料は docs/ 配下）。
- 事業者がコードを確認できるよう、リポジトリは Cursor でそのまま開ける構成にする。
- 変更はコミット単位で履歴を残し、要件定義書の版とコードの対応が追えるようにする。

### 7.2 運用保守（定常）
- 問題バンクの継続制作：AIで下書きを量産し、出典照合と答え・解説の検証を経て公開するフローを定型化する。
- 教材の定期見直し：IPA「情報セキュリティ10大脅威」の年次更新、規格・ガイドラインの改定、重大インシデントの教訓に合わせて改訂し、版を更新する。
- リマインドとレポートの定期実行、障害・問い合わせ対応。
- データのバックアップと復旧手順の確認（定期）。

### 7.3 改善
- 正答率・受講率のデータから弱点テーマと離脱ポイントを把握し、教材と問題を改善する。
- 利用企業からのフィードバックを収集し、機能改善の優先順位をつけて反映する。
- 年に1回、要件定義書自体を見直し、版を上げる。

## 8. 体制と役割
- 事業者（梅原基樹）：要件の決定、教材・問題の最終確認、利用企業との調整。
- Muse：設計・開発補助、問題下書きの照合支援、運用データの集計と改善案の提示。
- 外部AI（ChatGPT／Gemini等）：問題・教材の下書き生成（検証は必ず人間側の工程を通す）。

## 9. サイトとの役割分担
- サイト：教材の公開・周知（誰でも学べる）、サービスの紹介と登録への導線。
- アプリ：登録企業向けの受講・記録・集計・リマインド（教育の実施と証跡）。
- 両者は同じテーマ体系・教材資産を共有し、版管理の考え方をそろえる。

## 10. 未決事項・前提
- 課金：決済手段（クレジットカード決済サービスの利用等）、価格と課金単位（企業単位／人数単位）、無料プランの範囲の最終確定（体験6問の扱い）。
- 問題数の確定目標と制作ペース（開始時100〜200問→1,000問への拡大計画）。
- 記録の保持年数と、退職者・退会企業のデータの扱い。
- リマインドの配信チャネル（メール／アプリ内通知／その他）の確定。
- 運用基盤（ホスティング、バックアップ方式）と、個人情報の取扱いに関する体制・規約類の整備。
- 修了証の体裁と、誓約確認の法的扱いの確認。
- アグリゲーションの残件：JPCERT/CCへの商用利用確認（広報窓口宛て）、国家サイバー統括室・警察庁の利用条件確認、icat for JSONをアプリに組み込むか別枠にするかの設計判断、フィードの取得間隔の確定。
